## Public description

Predicting Hotel Page Views on TripAdvisor (Rome)

Problem statement
Participants are asked to predict hotel page views on TripAdvisor for 4,599 Rome hotels using rich hotel metadata. Page views are a proxy for popularity/demand. This is a regression task: given features such as bubble ratings, star class, review counts, prices/discounts, awards, location grade, and a very large set of amenity flags, predict the number of page views for each hotel.

Files
- train.csv: Training data with hotel_id, features, and the target column views.
- test.csv: Test data with hotel_id and the same features as train.csv, but without the target.
- sample_submission.csv: A valid example submission containing hotel_id and views (predictions) for the test set.

Key columns
- hotel_id: Unique identifier for each row. Use this to align predictions to test rows.
- views: Target to predict (number of page views). Only in train.csv.
- Feature set: Numeric and categorical metadata. Examples include: bubble_rating (half-bubble granularity), class and class-related indicators, n_reviews, location_grade, discount and discount_perc, price_* columns, awards flags, photos count, and hundreds of amenities_* binary flags. The name field is also included and can be used for feature engineering if desired.

Evaluation metric
Submissions are evaluated using Root Mean Squared Logarithmic Error (RMSLE) between the true views and the submitted predictions.
- Let y_true be the true views and y_pred be the submitted predictions aligned by hotel_id.
- We sanitize predictions by replacing non-finite values with 0 and clipping negatives to 0.
- RMSLE = sqrt(mean((log1p(y_pred_sanitized) - log1p(y_true))^2)).
RMSLE is robust to heavy-tailed count distributions and emphasizes relative error, making it suitable for popularity counts.

Submission format
- A CSV file with exactly two columns in this order: hotel_id, views.
- hotel_id must match those provided in test.csv (order does not matter).
- views must be numeric predictions; negative or non-finite values will be treated as 0 during evaluation.

Modeling guidance
- Consider target transformations (e.g., modeling log1p(views)).
- Engineer features from the rich amenity flags and, optionally, from name.
- Handle missing values and high-cardinality features carefully.
- Use robust validation (e.g., stratification or grouped splits by bubble_rating and by view intensity) to avoid overfitting and ensure generalization.
